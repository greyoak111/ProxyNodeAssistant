# TextNodeAssistant v0.9.5 reset baseline

This document is the product and implementation baseline for the lean v0.9.5
reset line. The line starts from the stable v0.9.0 codebase. It does not keep
adding features to the former experimental v0.9.5 product.

## 1. Product boundary

TextNodeAssistant is a local-first client for deploying, maintaining,
diagnosing, backing up, and restoring an authorized VPS node.

The reset line completely retires the former experimental features below:

- controller/member roles, device admission, invitations, leases, fencing, or
  a trusted-device gate;
- private drive, Copyparty, ordinary drive accounts, local admin, credential
  escrow, and drive-specific UI;
- any menu, service, state, placeholder, or success check that depends on those
  retired features.

A managed SSH key is only a per-VPS login credential. It is not a device
identity, admission token, or controller role.

## 2. Authentication model

Every remote action independently asks for the target and one of two SSH
methods:

1. **Temporary password**: the password is handed only to the SSH layer for the
   current action. A temporary key, if created for automation, is revoked and
   deleted at the end of that action.
2. **Managed node key**: a key is stored and looked up by VPS plus SSH user. It
   may be rotated, archived, restored, or removed without affecting keys for
   other nodes.

Host-key verification remains mandatory. A saved host-key mismatch must stop
before credentials are sent.

## 3. Only one construction entry

Menu action `[1]` is the only operation allowed to upload, install, replace, or
upgrade the remote embedded toolkit. Other actions may perform their named
maintenance operation, but must not silently reinstall the toolkit.

Credential rotation remains a separate explicit action. It is not a second
installation path.

## 4. One reviewed installation plan

The Windows CLI and WPF frontend must feed the same in-memory `InstallPlan` and
the same validator. Android builds the matching wire plan and enforces the same
route, template, performance, port, preview, `APPLY`, and fail-closed semantics;
its platform-specific input constraints are documented below.
The user must explicitly choose every non-boolean plan item; an empty response
is invalid.

### Route topology

| Input | Internal value | Availability | Meaning |
|---:|---|---|---|
| `0` | `keep` | Existing node only | Keep the current routes; do not dismantle or replace them |
| `1` | `gray` | New or existing node | DNS-only hostname with the direct Reality route |
| `2` | `orange` | New or existing node | Cloudflare-proxied hostname with TLS/XHTTP |
| `3` | `dual` | New or existing node | Keep one gray Reality route and one orange XHTTP route |

Gray and orange identities are entered separately. Every required hostname and
certificate email has no default and must be typed by the user. Dual mode
requires two different hostnames.

### Cover template

- `0 / preserve`: existing nodes only;
- `R / random`: choose one of the 15 bundled templates, avoiding the current
  template when possible;
- `A / stable`: select deterministically from the hostname;
- `1` through `15`: use the exact bundled template.

### Performance

- `0 / preserve`: existing nodes only; make no performance-profile change;
- `1 / auto`: derive a profile from VPS CPU and memory;
- `2 / low`: prioritize a small memory/concurrency footprint;
- `3 / standard`: balanced general-purpose settings;
- `4 / high`: use more CPU and memory for throughput.

### WARP

- `0 / preserve`: do not install WARP when absent and do not change existing
  managed routing;
- `1 / ensure-on`: idempotently install or repair the local WARP proxy and its
  managed route.

The reset line does not expose a destructive “force off” choice inside action
`[1]`.

The current Android client accepts `ensure-on` only for a fresh node and offers
`preserve` after a node already exists. The Windows client presents both choices
and requires an explicit answer. This is an intentional statement of current
client behavior, not a promise that their input screens are byte-for-byte equal.

### Fixed coordinated ports

The only accepted port preset is:

- Reality production: `443`;
- Reality real-client shadow validation: `24443`;
- Cloudflare/XHTTP edge and restricted origin: `8443`;
- WARP loopback: `40000`.

These values are one tested topology, not four unrelated free-text fields.
Changing them requires all consumers—Xray, Nginx, firewall, exports,
diagnostics, rollback, and dismantling—to be changed together in a future
implementation.

### Backup and finish choices

Backup before change is mandatory and cannot be disabled. After a successful
run, the user may separately choose whether to prune redundant backups and
whether to open the 3x-ui panel through a loopback SSH tunnel. Neither finish
action may run after a failed construction stage.

## 5. No mutation before review

Action `[1]` must follow this order:

1. select target and SSH method;
2. perform read-only toolkit/node inspection;
3. collect and validate the complete plan;
4. display the full review, with certificate-email local parts masked;
5. require exact uppercase `APPLY`;
6. only then upload or mutate the remote node.

Any other response cancels without uploading the toolkit.

Run-specific input is passed through a random root-only file with mode `0600`.
It is consumed once and deleted. Fixed shared input filenames are forbidden.

## 6. Transaction and validation rules

- An existing node is backed up before mutation.
- Each stage is fail-closed: failure stops handoff, backup pruning, panel
  opening, and all later stages.
- Route changes are staged and committed only after structural, edge, and real
  client validation.
- Reality `24443` and Cloudflare/XHTTP `8443` acceptance remain manual: the user
  imports the printed link into a real client and actually browses through it.
- A manual success phrase must never be inferred from a port probe or generated
  by the application.
- A failed staged route restores the prior runtime topology and keeps the
  diagnostic/backup artifacts needed for recovery.

## 7. Privacy and persistence boundary

The distributable contains no real VPS IP, hostname, domain, email, account,
password, API token, or private key.

Locally persisted behavior preferences may contain route mode, cover choice,
performance, WARP, prune-after-success, and open-panel-after-success. They must
not contain route identities. Domains and certificate emails live only in the
current in-memory plan and its protected one-time remote input.

Optional history stores host, SSH user, port, label, and time. It never stores
the VPS password. Managed private keys remain in the platform's protected key
storage. Provider API secrets may enter a platform credential store only after
explicit consent and must never be printed in normal logs.

## 8. Upgrade and migration

The visible version remains `v0.9.5`, while the reset line carries a strictly
higher internal build revision. Action `[1]` compares version, revision,
completeness, and build identity rather than trusting the visible version
alone.

- From v0.9.0 or an older toolkit: perform a normal backed-up upgrade.
- From the former experimental v0.9.5: archive the retired feature metadata,
  stop and remove its managed device/drive services and gates, and install the
  reset toolkit without reinstalling the working x-ui node.
- From the same complete reset build: skip the toolkit upload and continue only
  with the explicitly selected plan.
- From a newer remote build: refuse downgrade and direct the user to a matching
  or newer client.

Retirement preserves possible user file roots in place; it does not present
them as an active drive, mount them, or promise a file-browser recovery
feature. The generated retirement archive records what was removed. The reset
client contains no drive UI.

## 9. Uninstall and dismantle are different

- **Action `[13]`, uninstall embedded toolkit**: remove only the remote
  TextNodeAssistant program package and launchers. Preserve x-ui/Xray, Nginx,
  WARP, routes, certificates, credentials, and backups. Only action `[1]` can
  install the toolkit again.
- **Action `[18]`, full dismantle and restore baseline**: download and verify a
  rescue archive first, require exact destructive confirmation, remove managed
  node construction, and restore the captured pre-install baseline when
  available. Preserve the SSH rescue path. A legacy node without a precise
  baseline requires the additional legacy-full confirmation.

Neither operation is an automatic file-drive deletion path. User file roots
preserved during experimental-feature retirement remain outside the active
reset product boundary.

## 10. Windows and Android contract

Both clients expose the same supported remote operation boundary and the same
route/template/performance/port/fail-closed vocabulary, but platform details and
some input constraints differ:

- Windows uses the validated Windows OpenSSH suite, Windows Credential Manager
  for consented provider secrets, a WPF GUI, and the Windows clipboard;
- Android uses the embedded SSH/SCP implementation, Android Keystore-backed
  secret storage, native Android screens, and Android clipboard/share flows.

An Android client can upload the embedded toolkit to a new VPS; it is not a
thin viewer that requires a previous Windows installation. Local action `[14]`
has platform-scoped behavior: Windows manages the current user's proxy
environment variables, while Android can route this app's provider-API requests
through `127.0.0.1:10808`. Android `[14]` does not proxy SSH or system traffic.

## 11. Release acceptance gates

A reset-line release is not complete unless tests demonstrate:

- all retired device/drive/admin strings are absent from active client UI and
  workflow code (except bounded retirement code and migration documentation);
- explicit selection and validation of all plan modes;
- no remote upload before exact `APPLY`;
- fixed port-preset propagation to every remote consumer;
- one-time root-only input cleanup;
- same-version internal-revision upgrade and downgrade refusal;
- fail-closed handoff/panel/cleanup behavior and transactional rollback;
- uninstall and dismantle preservation/confirmation semantics;
- privacy scans of source and packaged artifacts for real deployment data.
